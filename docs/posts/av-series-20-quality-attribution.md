## 「卡了」不是一个指标

用户说的「卡」，可能指完全不同的东西：

- 画面停住几秒，声音还在。
- 声音断续，画面正常。
- 画面糊了，但没有停。
- 延迟越来越高，像在打电话。
- 进房后一直黑屏。

这些现象的根因分布在四个不同的段。用一个「质量分」或「MOS」概括，看起来简单，实际上会把定位信息压没。工程上更可靠的做法是：**先分段，再判三态，最后看证据。**

## 四段归因

把一次通话拆成四段：

| 段 | 范围 | 能直接观测什么 | 不能直接得出什么 |
| --- | --- | --- | --- |
| Publisher 上行 | 采集、编码、发送、上行网络 | 发送帧率、码率、丢包、到达间隔 | 接收端是否解码成功 |
| SFU 入口/解析 | 收包、组帧、缺包、RTX | 收包率、帧完整性、解析失败 | 发布者采集是否正常 |
| SFU 扇出 | 选层、队列、重写、下行发送 | 目标码率、实际发送速率、队列深度 | 订阅者 jitter buffer 的状态 |
| Subscriber 下行/渲染 | 网络、jitter buffer、解码、渲染 | 接收统计、解码帧数、渲染帧数 | 服务端无法直接定义「订阅者卡顿」 |

关键边界：

- 服务端能看到「包有没有到」，但很难直接证明「用户看到了画面」。
- 订阅者侧的卡顿，服务端通常只能给 `unknown`，除非客户端上报了证据。
- 发布者侧的卡顿，服务端也只能间接归因，不能仅凭「没收到帧」断定是采集问题。

## 三态：healthy / degraded / unknown

每一段只允许三种结论：

- **healthy**：有足够证据表明这一段正常。
- **degraded**：有足够证据表明这一段异常。
- **unknown**：证据不足，不能下结论。

最重要的规则：**unknown 不能当成 healthy。** 很多「排查半天没发现问题」的案例，根源就是把「没数据」误判成「没问题」。

另一个规则：**必要非充分。** 比如「到达间隔正常」只能说明包还在来，不能说明解码器能解。丢了参考帧，后续帧照常到达，但画面可能已经花了。

## 关键指标

先认识一组够用的指标：

| 指标 | 回答什么问题 | 常见误读 |
| --- | --- | --- |
| 到达间隔 / Arrival Gap | 上游还有没有新帧到达 | 间隔正常不等于能解码 |
| 收包率 / 丢包率 | 网络是否在丢包 | 丢包率低也可能缺关键帧 |
| NACK / RTX 速率 | 重传是否频繁 | 有重传不代表一定恢复 |
| PLI / FIR 速率 | 是否在反复请求关键帧 | 高 PLI 可能是解码器一直缺参考帧 |
| jitter | 到达抖动 | 平均值会掩盖尖峰 |
| RTT | 往返延迟 | 低 RTT 也可能带宽不足 |
| target bitrate | 发送侧目标码率 | 目标值不是实际发送值 |
| 实际发送速率 | 真正发出去多少 | 要和时间段、分层一起看 |
| quality limitation reason | 发送侧认为的限制原因 | 不是永远可信的根因 |
| 队列深度 | 扇出是否在排队 | 队列深不等于网络差 |

看指标时优先看 P95/P99 和时间序列，不要只看平均值。卡顿往往是短时尖峰，平均值会把尖峰抹平。

## 为什么 `quality_limitation_reason=bandwidth` 会骗人

很多发送侧实现会给出 `qualityLimitationReason`，常见取值是 `none`、`cpu`、`bandwidth`、`other`。直觉上，看到 `bandwidth` 就说明带宽不足。但在某些「注入编码帧」的发送路径里，这个字段可能被带宽估计的瞬态置成 `bandwidth`，而且不会自动回落到 `none`。

结果就是：链路很干净，实际发送速率也贴着目标，但指标一直显示 `bandwidth`。如果直接把它当根因，就会误判为「下行带宽不足」，去做降层、限码率，反而把问题放大。

正确的做法是交叉验证：

- `reason=bandwidth` 时，看**实际发送速率**是否真的贴着 `target_bitrate`。
- 同时看丢包、RTT、NACK、队列深度。
- 如果实际发送速率没有受限、丢包也正常，就只能记 `unknown`，不能记 `degraded`。

`reason=none` 也不是永远健康。它可能只说明发送侧没有触发限制逻辑，不代表接收端解出来了。

## 为什么 `available_outgoing_bitrate` 不能单独用

`available_outgoing_bitrate` 是一个估计值，不是「网络实际允许的硬上限」。它可能：

- 在 BWE 爬升阶段偏高。
- 在注入式发送路径里与实际限速不一致。
- 只反映某条候选路径的估计，不覆盖接收端瓶颈。

所以它不能单独拿来判断「带宽够不够」。更有用的组合是：

```text
target_bitrate
  + 实际发送速率
  + 丢包 / RTT / NACK
  + 队列深度
  + 质量限制原因
```

单看任何一个，都容易得出相反结论。

## 指标与 CDR 的分工

指标适合聚合看趋势，CDR 适合按实体下钻。两者不要混：

- **指标**：标签必须是有界枚举或分桶，不能带 `room_id`、`session_id`、`participant_id`、`track_id`、IP、token。基数一高，监控系统会被打爆。
- **CDR**：一次会话一行，可以带不透明 ID、事件时间线、每 Track 的统计，用于投诉排查。

一个实用原则：**要按实体查的进 CDR，要看整体趋势的进指标。** 不要把用户 ID 塞进指标标签，也不要用指标去还原某个具体用户。

## 排查顺序

遇到「卡了」，按这个顺序走：

1. **定义症状**：谁、哪个方向、什么时间、持续多久、是否可复现。
2. **切段**：先判断是上行、入口、扇出还是下行/渲染。
3. **标三态**：每段给 healthy / degraded / unknown，不要跳过 unknown。
4. **找交叉证据**：至少两个独立指标指向同一段，才下结论。
5. **再做动作**：降层、请求关键帧、限码率、换路、重启 PC，分别对应不同段，不要一上来就全套。

一个常见的错误是「看到丢包就降码率」。如果丢包发生在订阅者下行，降发布者码率可能没用；如果丢包发生在 SFU 入口，降下行码率也可能没用。先切段，再动作。

## 五个常见误区

- **用 MOS / 质量分代替分段。** 分数低不等于知道原因。
- **把 unknown 当 healthy。** 没数据就是没数据。
- **只看平均值。** 卡顿通常是短时尖峰。
- **把 `quality_limitation_reason` 当根因。** 它只是发送侧的判断，可能失真。
- **在指标里放实体 ID。** 基数爆炸，最后监控先挂。
