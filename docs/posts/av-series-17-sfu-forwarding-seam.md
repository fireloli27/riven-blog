## SFU 的最小定义

SFU（Selective Forwarding Unit）做三件事：

1. 接收每个发布者的上行媒体。
2. 按每个订阅者的需求，选择要转发的内容。
3. 把选中的媒体重新发给订阅者。

在「透传」模式下，SFU 不创建编码器，也不创建解码器。它不把 VP8 解成 YUV，也不把 YUV 重新压成 VP8。它处理的是已经编码好的帧和 RTP 包。

但「不编解码」不等于「不碰包」。SFU 仍然要解析 RTP、重组帧、改写头部、重新打包，否则无法做选层、拥塞控制和多订阅者扇出。

## 逐包转发的五个坑

假设 SFU 收到一个上行包，直接复制给三个订阅者。听起来很省事，但很快就会遇到问题：

| 问题 | 直接复制会怎样 | SFU 必须做什么 |
| --- | --- | --- |
| 下行 SSRC | 多个订阅者看到同一个 SSRC，状态互相污染 | 为每个下行流分配独立 SSRC |
| 序号连续 | 丢包或跳层后，下行 `seq` 出现缺口 | 按下行流重写 `seq` |
| 时间戳 | 换层后上游时间戳跳变，接收端丢帧 | 按订阅权重锚输出时间戳 |
| RTCP | NACK/PLI 不知道是哪条下行流 | 每个下行流维护独立 RTCP 状态 |
| 选层 | 包已经转发出去，无法再改 | 先组帧、再决策、最后打包 |

关键在最后一行：**一旦把包发出去，就没有反悔机会**。要做「这个订阅者应该降层」这种决策，必须在发送前掌握完整帧，而不是手里只有一个孤立的包。

## 什么是「包缝」

「包缝」是网络包和媒体帧之间的交界处。上游进来的是 RTP 包，下游需要的是可决策的帧；SFU 在包缝上完成转换：

```text
上行 RTP 包
   │
   ▼
┌──────────────────┐
│ 解析 RTP 头       │  seq / timestamp / SSRC / marker
│ 解析 payload 头   │  VP8 descriptor / H.264 FU-A
│ 按帧重组          │  收齐一帧，或判定缺口
└────────┬─────────┘
         │ 完整帧 + 元数据
         ▼
┌──────────────────┐
│ 转发决策          │  选层、丢帧、请求关键帧
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ 改写 + 重新打包   │  新 SSRC / seq / timestamp
└────────┬─────────┘
         │
         ▼
下行 RTP 包
```

这条链路里，SFU 不需要解码画面，但需要理解「帧的边界」和「包的边界」。这就是包缝的难点：它比纯包转发多一层媒体语义，又比转码轻得多。

## 视频帧怎么重组

不同 codec 的 payload 格式不同，但组帧思路相似：

- **VP8**：payload descriptor 里有 `S` 位（是否是帧/分区的开始）和 `PID`（分区 ID）；结合 RTP `marker` 判断帧结束。
- **H.264**：常见 FU-A 分片，靠 `S`/`E` 位标记分片起止；STAP-A 可以聚合多个 NAL Unit。
- **通用信号**：RTP `marker=1` 通常表示当前帧的最后一个包。

组帧器至少要回答三个问题：

1. 这个包属于哪一帧？看 SSRC + timestamp。
2. 这一帧的包齐了吗？看 `seq` 是否连续、有没有缺口。
3. 这是一帧的开始还是中间？看 payload 头和 `marker`。

如果发现缺口，正确做法通常是**整帧丢弃**，而不是把残缺帧交给解码器。残缺帧可能让解码器报错、花屏，甚至污染后续参考帧。丢弃后可以请求关键帧，让解码器重新对齐。

### RTX 不是坏包

生产环境里，丢包后可能收到 RTX 重传包。RTX 通常有独立的 SSRC 和 payload type，包内还带原始 `seq`。组帧器要把它当成「补洞」，而不是「格式不对的坏包」。

如果把 RTX 当解析失败直接丢掉，表现就是：明明有重传，接收端还是花屏；日志里还会出现大量莫名其妙的 payload 解析错误。

## 透传到底透传什么

「透传」常被误解成「逐字节复制」。更准确的定义是：

- SFU 不在 SDP 之外创建该 codec 的编码器/解码器。
- SFU 不拥有画面，不做转码、混流、合成。
- SFU 仍然解析 payload 头、重组帧、改写 RTP 头、重新打包。

所以透传的判断标准不是「有没有调用 codec 的 Create」，而是「有没有真正创建并使用编解码器」。一个 SFU 可以声明支持 VP8，但从不创建 VP8 解码器；它只是把 VP8 的帧转给能解码的接收端。

这也解释了一个常见现象：日志里看到 codec 的 `Create()` 被调用，不代表真的在解码。某些实现会在关键帧到达时尝试创建解码器，但返回空；判断时要看 `frames_decoded` 和实际输出，而不是只看调用次数。

## 为什么必须掌握帧级信息

下面这些能力，都依赖「完整帧 + 元数据」，而不是单个包：

- **选层**：这个订阅者当前该收哪一层？
- **关键帧门控**：换层后，等新层关键帧到了再切。
- **整帧丢弃**：缺包的帧不能交给解码器。
- **到达间隔观测**：按 RTP timestamp 变化判断「有没有新帧」。
- **拥塞响应**：根据目标码率和实际发送速率决定降层或降码率。
- **按订阅者重写**：每个下行流的 SSRC、seq、timestamp 独立。

如果 SFU 只做包级转发，它只能做「固定转发」；一旦要做自适应，就必须上升到帧级。

## 常见失败模式

- **只转发半个帧**：接收端解码器报错，后续帧也解不出来。
- **把 RTX 当坏包**：重传失效，丢包被放大。
- **不判 `seq` 缺口**：残缺帧进入解码器，花屏持续时间不可控。
- **时间戳直接透传**：换层时出现巨大跳变，jitter buffer 丢整段。
- **下行 `seq` 不连续**：接收端误判丢包，NACK 风暴。
- **0×0 尺寸**：某些实现会在后续编码/注入路径里触发断言，直接崩进程。

这些失败模式有一个共同点：它们在「包看起来正常」时也可能发生。只看 RTP 头不够，必须看帧的完整性和时间线。
