## 为什么需要 Simulcast

一个发布者的上行带宽有限，但订阅者的下行条件各不相同：

- 大屏、好网络，想看 720p。
- 手机、弱网，只能承受 180p。
- 有人只是听声音，视频可以降到很低。

如果发布者只发一路 720p，SFU 要么原样转发（弱网订阅者卡），要么转码（SFU 成本和延迟上升）。Simulcast 的做法是：发布者同时编码多档清晰度，每档一条流；SFU 给每个订阅者选一档转发，不转码。

这就是「用上行带宽换下行灵活性」。

## Simulcast 与 SVC

两者都提供多层，但实现方式不同：

| 维度 | Simulcast | SVC |
| --- | --- | --- |
| 上行流数量 | 多层通常是多条独立流 | 通常一条流内包含多层 |
| 层标识 | 每层一个 SSRC，常配 `rid` | 层信息在编码流内部 |
| 编码器 | 每层独立编码 | 一次编码产生空间/时间层 |
| SFU 选层 | 选一条流转发 | 从一条流里选层转发 |
| 典型 codec | VP8、H.264 | VP9、AV1 等 |
| 兼容性 | 浏览器支持广 | 依赖 codec 和实现 |

Simulcast 的优点是简单、兼容性好；缺点是上行要发多份，编码和带宽成本高。SVC 的上行更省，但编码器、SFU 和接收端支持更复杂。

VP8 的 temporal scalability 只提供帧率层，不等同于完整的空间 SVC。讨论「SVC」时要明确是空间层还是时间层，否则很容易把两个概念混在一起。

## 上行：一层一条流

一个三层的 simulcast 发布者，通常会发三条独立的编码流：

| 层 | 分辨率示例 | 典型用途 | 标识 |
| --- | --- | --- | --- |
| 低 | 320×180 | 弱网、小窗 | SSRC + `rid=0` |
| 中 | 640×360 | 普通手机 | SSRC + `rid=1` |
| 高 | 1280×720 | 大屏、好网络 | SSRC + `rid=2` |

每层有自己的 SSRC、码率、帧率和关键帧节奏。SFU 在上行侧看到的是「同一个 Track 的三条流」，而不是一条流里的三个层。

层的身份首先靠 SSRC 认定；`rid` 主要用于 SDP 协商和诊断。只靠 `rid` 做运行时路由不够稳，因为不同实现、不同重协商阶段对 `rid` 的处理并不完全一致。

理想情况下，三层的关键帧是对齐的：同一时刻各层都从关键帧开始。这样 SFU 换层时不用等太久。但编码器不保证永远对齐，所以换层逻辑必须能处理「新层还没有关键帧」的情况。

## 下行：一个订阅者一条流

这是最容易混淆的地方：**上行是一层一条流，下行可以是一个订阅者一条流**。

对某个订阅者来说，SFU 只给它发一条视频 RTP 流，使用一个固定的下行 SSRC。订阅者不需要知道背后有多少层，也不需要为每层维护一套接收状态。SFU 在内部把「当前选中的上行层」的帧，重写后注入这条下行流。

```text
发布者上行                      SFU                         订阅者下行
  720p 流 ─┐
  360p 流 ─┼─► 选层器 ─► 重写 SSRC/seq/ts ─► 一条下行流（一个 SSRC）
  180p 流 ─┘
```

这样做的好处：

- 接收端只有一个 jitter buffer、一套 RTCP 状态、一个带宽估计。
- 换层不需要重新协商 SDP，也不需要新增 m-line。
- 每个订阅者的 NACK、PLI、RTX 状态互不干扰。

代价是：接收端会看到「同一个 SSRC 的分辨率变了」。这要求 jitter buffer 和解码器能处理同流分辨率跳变。libwebrtc 对 libwebrtc 的验证是一个层面，浏览器、移动端、不同解码器是另一个层面，不能直接画等号。

## 选层依据

选层器通常看这些输入：

| 输入 | 作用 |
| --- | --- |
| 带宽估计 / 目标码率 | 判断当前能承受哪一档 |
| 丢包率、RTT、NACK 速率 | 判断链路是否在恶化 |
| 接收端分辨率、窗口大小 | 太高的层可能没有意义 |
| CPU / 解码能力 | 弱设备不适合高分辨率 |
| 订阅状态 | 暂停、恢复、切源 |

实际实现需要**滞回**：降层要果断，升层要保守。否则带宽在阈值附近抖动时，会反复换层，每次换层都可能触发关键帧请求，形成恶性循环。

一个常见的策略是：

- 带宽下降：先降层，再考虑降帧率/码率。
- 带宽恢复：不要立刻升层，等稳定一段时间，并且在新层关键帧到达后升。
- 升层前确认新层的码率不会把总发送速率推过目标。

## 换层时序

一次换层大致是：

```text
t0  选层器决定：720p → 360p
t1  如果需要，向新层请求关键帧（PLI/FIR）
t2  等待新层关键帧到达
t3  关键帧到达，切换源
t4  重锚输出时间戳
t5  丢弃旧层在途包，开始稳定发送新层
```

降层通常比升层快，因为低层可能已经有最近的关键帧；升层往往要等一个 GOP。最坏情况下，换层延迟是「一次 RTT + 一个关键帧间隔」。

换层不是「改一个指针」就结束。旧层可能还有在途包，新层的关键帧可能很大，接收端的 jitter buffer 可能还在等旧层的时间线。这些都要处理。

## 代价与坑

- **关键帧请求风暴**：多个订阅者同时换层，同时发 PLI，发布者会被关键帧压垮。
- **关键帧太大**：高分辨率关键帧可能瞬间超过目标码率，造成排队和延迟。
- **旧层在途包**：切换后旧包到达，接收端可能按旧时间戳处理，造成回退或抖动。
- **RTX 状态断层**：换层后 NACK 可能指向旧层序号，重传映射要能处理。
- **同 SSRC 分辨率跳变**：接收端 jitter buffer/decoder 必须支持；浏览器兼容性要单独验证。
- **滞回不足**：在阈值附近来回切，用户体验比稳定低层更差。

## 四个常见误解

- **Simulcast 不是 SVC。** 前者通常是多条独立流，后者通常是一条流内多层。
- **`rid` 不是唯一身份。** 运行时路由最终要落到 SSRC 和实际收到的流。
- **换层不是换下行 SSRC。** 单流下行模型里，订阅者看到的是一个固定 SSRC。
- **关键帧请求不是免费的。** 它会增加发布者上行负担，也会增加延迟。
