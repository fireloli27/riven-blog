## 一帧不是一包

编码器输出的是一帧画面，但网络上传的是一串包。两者不是一一对应：

- 一帧视频可能拆成 1 个到几十个 RTP 包；大关键帧尤其容易拆多包。
- 一帧音频通常就是一个 RTP 包；Opus 常见帧长是 20 ms。
- 接收端必须先判断「这一帧的包收齐了没有」，再交给解码器。

```text
采集帧
  └─ 编码器 ──► 一帧压缩数据
                   ├─ RTP 包 1
                   ├─ RTP 包 2
                   └─ RTP 包 3
                              │
                         网络传输
                              │
                   ┌──────────┴──────────┐
                   │   jitter buffer     │
                   │  重排、等待、判完整  │
                   └──────────┬──────────┘
                              │
                         解码器 ──► 一帧画面
```

RTP 的任务不是「可靠传输」，而是「把实时媒体切成包，并让接收端能重排、判丢、按时间播放」。可靠性由 RTCP 反馈和重传机制补，不是靠 TCP 重传一切。

## RTP 头：先认识六个字段

RTP 头最少 12 字节。初学先抓住下面六个字段，其他字段可以后面再补。

| 字段 | 长度 | 一句话作用 | 常见误解 |
| --- | --- | --- | --- |
| `payload type` | 7 bit | 告诉接收端 payload 是什么编码 | 它不是固定值，通常由 SDP 动态协商 |
| `sequence number` | 16 bit | 包序号，用来判丢包和重排 | 它不是帧号，会回绕 |
| `timestamp` | 32 bit | 媒体采样时钟，用来定播放时间 | 它不是墙上时钟，也不是毫秒 |
| `SSRC` | 32 bit | 一条 RTP 流的身份 | 它不是用户 ID，也不是 Track ID |
| `marker` | 1 bit | 标记一帧的最后一个包，或一段话音结束 | 它不表示「这个包最重要」 |
| `payload` | 变长 | 编码后的媒体数据 | 它可能还带 codec 自己的 payload 头 |

### sequence number

`seq` 从 0 到 65535，然后回绕。接收端看到 `100, 101, 103`，就知道 102 可能丢了；看到 `100, 101, 102` 但顺序是 `101, 100, 102`，就知道发生了乱序。

`seq` 是**包级**的，不是帧级。一帧拆成三个包，会有三个连续的 `seq`；下一帧再从下一个号继续。

### timestamp

`timestamp` 是媒体时钟，不是 Unix 时间。视频通常用 90 kHz，音频（Opus）用 48 kHz。它回答的是「这一帧应该在媒体的哪个时间点播放」，不是「这个包什么时候到」。

同一帧的多个 RTP 包共享同一个 `timestamp`；下一帧的 `timestamp` 增加一个帧间隔。30 fps 视频一帧是 `90000 / 30 = 3000` tick。

### SSRC

`SSRC` 是一条 RTP 流的同步源标识。它通常对应「一个编码器输出的一条流」：

- 一个摄像头的一路编码，可以是一个 SSRC。
- simulcast 的三层，通常是三个 SSRC。
- 一个订阅者的下行流，可以是另一个 SSRC。

它不是 Participant ID。同一个用户可以有多个 Track、多个 SSRC；不同用户也可能复用同一个数值（冲突时由 RTCP 处理）。

### marker

视频里，`marker=1` 通常表示「这是当前帧的最后一个 RTP 包」。接收端看到它，才可以尝试组帧。音频里，`marker=1` 常用来标记一段话音的开始或结束，具体看 codec 和实现。

## 一个 30 fps 视频帧的例子

假设第一帧从 `seq=100` 开始，`timestamp=0`，拆成三个包：

| 包 | seq | timestamp | marker | 含义 |
| --- | --- | --- | --- | --- |
| 1 | 100 | 0 | 0 | 第一帧的第 1 个包 |
| 2 | 101 | 0 | 0 | 第一帧的第 2 个包 |
| 3 | 102 | 0 | 1 | 第一帧的最后一个包 |
| 4 | 103 | 3000 | 0 | 第二帧的第 1 个包 |
| 5 | 104 | 3000 | 1 | 第二帧的最后一个包 |

如果包 101 丢了，接收端会看到 `100, 102, 103...`。它可以：

1. 先等一会儿，看 101 会不会重传回来。
2. 发 NACK，请求重传 101。
3. 如果等不到，第一帧就不完整，通常整帧丢弃，并请求一个关键帧。

这就是为什么「丢一个包」有时只是轻微花屏，有时会卡住好几秒：关键帧缺一块，后续帧都参考不了。

## RTCP：接收端怎么把问题告诉发送端

RTP 负责送媒体，RTCP 负责送反馈。两者通常成对出现。先认识五类反馈：

| 反馈 | 作用 | 典型触发 |
| --- | --- | --- |
| Receiver Report | 汇报收包率、丢包率、jitter | 周期性发送 |
| NACK | 请求重传某个 `seq` | 发现缺包 |
| PLI / FIR | 请求一个关键帧 | 解码器缺参考帧、刚订阅、换层 |
| REMB | 接收端告诉发送端可用带宽 | 带宽估计 |
| TWCC | 传输层拥塞控制反馈 | 逐包到达时间 |

RTCP 不是媒体数据，它走单独的包，但通常和 RTP 复用同一条五元组（`rtcp-mux`）。初学可以把 RTCP 理解成「接收端给发送端写的状态报告和请求单」。

## jitter buffer：为什么不能来一包解一包

网络包到达的时间间隔不会刚好等于帧间隔。jitter buffer 做三件事：

1. **重排**：按 `seq` 把乱序包放回正确位置。
2. **等待**：给迟到的包一点时间，避免刚丢就解码。
3. **判完整**：一帧的包齐了，才交给解码器。

它是在「延迟」和「流畅」之间做交换。缓冲太小，网络一抖就卡；缓冲太大，通话延迟高。

时间戳在这里很关键：接收端用 `timestamp` 判断帧与帧的间隔。如果时间戳突然从 `900000` 跳到 `123456789`，jitter buffer 会认为中间隔了非常久，可能直接清空缓冲、丢掉一大段。这就是后面「换层必须重锚」的根因。

## 三个常见误解

- **`seq` 不是帧号。** 一帧可能对应多个 `seq`，一帧也可能只对应一个。
- **`timestamp` 不是墙上时钟。** 它没有时区、不是毫秒，也不保证和真实时间线性对应；它只描述媒体时间线。
- **`SSRC` 不是用户。** 它是流标识；用户、Track、订阅关系都在更高的信令层。

## 怎么自己看

- Wireshark 过滤 `rtp`，展开 RTP 头，观察 `seq`、`timestamp`、`SSRC`、`marker`。
- Chrome 打开 `chrome://webrtc-internals`，看 `outbound-rtp` / `inbound-rtp` 里的 `ssrc`、`packetsSent`、`packetsReceived`、`jitter`。
- 用 `ffmpeg` 或 `srs` 之类工具推一路流，抓包对比「一帧几个包」。
