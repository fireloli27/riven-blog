本文是「音视频学习工程」系列第 21 篇，也是这一段的收尾。前面二十篇讲的是概念和机制；这一篇讲方法：拿到一份 SFU 设计文档，应该按什么顺序读，问哪些问题，怎么避免被术语淹没。

**本文覆盖：** 推荐阅读顺序；每篇文档只问三个问题；一张检查清单；要画的三张图；常见阅读误区。

**本文不覆盖：** 具体产品的内部设计；任何未公开的实现细节；选型结论。

上一篇：[怎么判断「卡了」](/posts/av-series-20-quality-attribution)。

## 不要从第一篇 ADR 顺着读

很多设计文档按编号排列，但编号不等于阅读顺序。第一篇可能是「房间亲和性」，第二篇可能是「信令语言选型」，这些都属于控制面；媒体主链路反而在后面。

如果一上来读控制面，会遇到大量「Room、Node、Session、Slot」之类的词，却不知道媒体包怎么走，越读越抽象。

更有效的顺序是：**先媒体，后控制；先数据路径，后管理路径。**

## 推荐顺序

### 第 0 步：术语表

先读 GLOSSARY 或术语表，只做一件事：把不认识的词标出来。不要背，也不要试图一次理解所有关系。

重点找这些词：

- Track、Subscription、Publisher、Subscriber
- Frame、Layer、Simulcast、SVC
- Packet、RTP、SSRC、Timestamp
- Session、Participant、Slot

如果术语表里已经区分了「Session 不是 Participant」「Frame 不是 webrtc::VideoFrame」，说明作者在认真控制语义，后面读起来会省很多力。

### 第 1 步：媒体管线

找一篇讲「采集 → 处理 → 编码 → 发送 / 接收 → 解码 → 渲染」的文档。只回答：

- 谁拥有采集？
- 谁拥有编码器？
- AI 处理插在哪一侧？
- 哪些线程负责哪些段？

这一步的目标是画出第一张图：**一帧从采集到渲染的路径**。

### 第 2 步：编码基线

找 codec 选型文档。只问：

- v1 的基线 codec 是什么？
- 是否使用 simulcast？几层？
- 是否转码，还是透传？
- 音频和视频的基线是否分开？

不要在这一步纠结专利、硬件兼容性、所有平台的编解码矩阵；那些是后续增量。

### 第 3 步：转发缝

这是 SFU 文档的核心。找讲「包缝 / forwarding seam / 透传」的文档。只问：

- SFU 是否解码/编码？
- 转发单位是包、帧还是流？
- 如何判断一帧完整？
- 丢包、RTX、seq 缺口怎么处理？
- 时间戳是否改写？

这一步要画出第二张图：**一个上行 RTP 包到下行 RTP 包的路径**。

### 第 4 步：下行模型

找讲「单流下行 / 多层上行 / 换层」的文档。只问：

- 上行是一层一条流，还是一条流多层？
- 下行是每个订阅者一条流，还是每层一条流？
- 换层时 SSRC 变不变？
- 关键帧怎么请求、怎么门控？
- 时间线怎么重锚？

这一步要画出第三张图：**一次换层的时间线**。

### 第 5 步：可观测性

找指标契约和排查手册。只问：

- 哪些指标有界，哪些进 CDR？
- 四段归因怎么分？
- 哪些段只能记 `unknown`？
- 哪些阈值是实测，哪些是推算？

如果文档把「unknown」当「healthy」，或者指标里带实体 ID，说明可观测性设计还不成熟。

### 第 6 步：信令与控制面

最后再读 Session、Resume、鉴权、调度、Node 注册。此时你已经知道媒体怎么走，控制面的每个状态才有落脚点。

控制面文档可以问：

- 断线重连时，PC 和媒体是否保留？
- Session 和 Participant 的生命周期是否一致？
- 鉴权发生在 Join 还是每次消息？
- 节点注册和运营接口是否共用一个信任域？

## 每篇文档只问三个问题

不管是 ADR、研究笔记还是设计说明，读完一篇至少回答：

1. **单位是什么？** 包、帧、Track、Subscription、Session，还是 Room？
2. **状态归谁？** 这个状态在客户端、SFU、Signaling 还是 injector 侧？
3. **这是实测还是推断？** 有没有探针、日志、抓包或对照实验支撑？

这三个问题能过滤掉大部分「读懂了字，但没读懂设计」的情况。

## 一张检查清单

| 问题 | 为什么重要 | 典型证据 |
| --- | --- | --- |
| 转发单位是包还是帧？ | 决定能否选层、判完整、重写时间戳 | 包缝文档、组帧器设计 |
| 是否解码/编码？ | 决定成本、延迟、codec 约束 | 是否创建 codec、`frames_decoded` |
| 上行几层、下行几条流？ | 决定 SSRC、RTCP、jitter buffer 状态 | simulcast/下行模型文档 |
| 换层时时间戳怎么处理？ | 直接决定会不会卡几秒 | 重锚算法、数值例子 |
| 关键帧怎么请求？ | 决定换层延迟和发布者压力 | PLI/FIR、关键帧门控 |
| 丢包/RTX 怎么处理？ | 决定花屏和重传是否有效 | 组帧器、RTX 映射 |
| 队列和拥塞控制在哪？ | 决定延迟和降层策略 | 扇出队列、BWE 文档 |
| 质量怎么归因？ | 决定能不能定位问题 | 四段归因、三态 |
| 哪些数字是实测？ | 决定能不能用于生产 | 标定记录、探针报告 |
| 失败模式是什么？ | 决定实现期会不会踩坑 | 0×0、缺关键帧、半帧 |

## 要画的三张图

读文档时，尽量自己画，不要只看文字：

1. **帧路径**：采集 → 处理 → 编码 → 发送 → 接收 → 解码 → 渲染。
2. **包路径**：上行 RTP → 组帧 → 决策 → 重写 → 下行 RTP。
3. **状态机**：Join / Publish / Subscribe / Resume / Leave 的状态变化。

画不出来，通常说明还有概念没打通；画出来后发现两条路径对不上，通常说明文档里有矛盾。

## 五个阅读误区

- **从 libwebrtc 源码开始。** 源码是实现细节，不是架构入口；先懂数据流，再看代码。
- **按 ADR 编号顺序读。** 编号是记录顺序，不是学习顺序。
- **把研究笔记当现行结论。** 研究笔记可能已被后续 ADR 推翻，先看有没有「已被取代」的标记。
- **忽略「未验证」。** 文档里写「推测」「待标定」「未实测」的地方，往往就是实现期最大的风险。
- **把控制面当媒体面。** Session、Room、Node 很重要，但它们不告诉你 RTP 包怎么走。

## 系列收尾

这一系列从「一帧怎么变成 RTP 包」讲到「怎么判断卡在哪」，覆盖了读 SFU 设计文档所需的最小知识面：

- 媒体：帧、编码、关键帧、GOP。
- 传输：RTP、RTCP、NACK、RTX、jitter buffer。
- 连接：SDP、m-line、transceiver、ICE、DTLS-SRTP。
- 架构：SFU、包缝、透传、simulcast、换层、重锚。
- 工程：四段归因、三态、指标与 CDR。

接下来如果继续写，可以往三个方向走：抓包实战、用一个最小 SFU 跑通一条链路、或者逐篇拆解一份真实的架构文档。无论哪条，建议都从「画图 + 提问题」开始，而不是从背术语开始。
